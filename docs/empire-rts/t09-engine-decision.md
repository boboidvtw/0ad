# T09 引擎修改決策

狀態：DONE（決策文件）。2026-09-20開始，2026-09-21完成文件同步及核對。

**決策：維持官方 R28 0.28.0 與現有獨立 Mod；本階段不啟動 C++ 修改。** 防空保留已驗收的即時傷害；完整潛艇、精確飛行彈道、精準跑道／停機位延後。這是已選定範圍下的架構決策，不是保證 Mod 能滿足所有未來需求。

本次只變更文件與證據核對紀錄，沒有新增玩法或執行新的引擎場次。起點 `ac4cbff`、master、clean。本決策以 [T07驗收](evidence/t07-validation.md)、[T08驗收](evidence/t08-validation.md) 及對應機器結果為依據；[T09核對紀錄](evidence/t09-decision-audit.json)記錄來源和runtime的現況比對。

## 1. 決策範圍與證據等級

- 已驗證：T07兩seed各36項及GUI；T08兩seed各30項、四狀態GUI、M1回歸。重播僅事件／結果一致，沒有逐回合hash，不代表多人同步。
- 已重現限制：T07精確飛行彈道未成立；T08原生攻擊對hidden目標仍可扣血。後者不是遊戲需求通過，而是需處理的缺口。
- 設計候選：專用Mod攻擊檢查、自動偵測、浮潛controller及停機位預約。未實作、未以引擎驗收；不把能寫JavaScript視為可行性證明。
- Insufficient data：3D水下碰撞／尋路的必要性、規模化性能、完整同步、匹配R28原始碼的建置成本。沒有工作日估算或新付費依賴承諾。

## 4. T16攻擊檢查的最小驗證契約（TODO）

此節是可實作規格，未修改目前Attack元件。T16先保留固定深水與手動狀態fixture，單獨證明攻擊規則，再讓T17接上玩家操作與自動偵測。

1. **範圍**：隔離海戰沙盒，只有專用武器模板可參與。新元件接管這些實體的攻擊生命週期；原生M2與既有T07不改。測試船／潛艇不可放進包含未受控攻擊者的正式對局。
2. **狀態權威**：由目標實體的潛航狀態判斷是否在水下，不能只看模型高度、GUI狀態或可變顯示名稱。偵測按攻擊者玩家計算，並要求普通LoS；未知／無效狀態拒絕發射。
3. **每次發射條件**：雙方存活且在世界中、敵對、合法武器／目標類別、距離、目標可見／被偵測、攻擊者不在切換或停火中。所有權與外交在發射時重查。
4. **入口覆蓋**：新命令、已在進行的攻擊、自動索敵、直接PerformAttack呼叫；只擋GUI或只改CanAttack不算完成。若新元件仍呼叫原生PerformAttack，必須確保所有可達入口經過同一檢查。
5. **原子性**：同一simulation turn採一致事件順序；同回合失去偵測、轉敵、死亡不得留下未檢查的後續發射。已在合法條件下完成的即時傷害不回滾；延遲命中不在最小範圍。
6. **武器矩陣**：艦砲可打可見水面船，拒絕已偵測水下船；反潛可打已偵測水下船；魚雷可打合法敵船／已偵測潛艇，拒絕友方、陸軍、建築、飛機。被拒絕案例必須觀察實際HP不變，不只回傳false。
7. **範圍撤銷**：失去偵測後停止發射並清除鎖定，恢復偵測不自動恢復舊的強制命令，除非新規格明定且驗收；死亡／轉敵同理。
8. **DoD**：重現T08兩個漏傷案例的前後對照；拒絕案例連續至少3次原武器週期HP不變，允許案例至少一次實際傷害；兩seed、固定來源、事件／結果重播、必要M1回歸。若觸及共享攻擊／命令路徑，再跑受影響M2／T07回歸。GUI未改不以靜態驗證宣稱GUI已完成。

混用原生攻擊者是明確的整合關卡：專用攻擊元件只保護參與該規則的攻擊者，不能推定其他原生武器也會尊重水下狀態。正式整合前須枚舉所有合法攻擊來源；若無法封閉入口，再按第5節重開方案比較。

## 5. 重新考慮引擎修改的門檻

只有具體必要需求遇到可重現的Mod限制，才啟動新引擎工作；任一門檻觸發僅表示重開比較，不是自動批准修改全部引擎。

| 觸發情況 | 必須取得的證據 | 下一動作 |
| --- | --- | --- |
| 隱蔽目標仍從無法接管的原生路徑受傷，且該攻擊來源必須納入 | 最小場景、entity／owner／weapon／事件順序、HP前後值；專用Mod與共享JS替代方案的結果 | 比較局部JS與native變更，先列受影響回歸 |
| 必須讓不同深度單位互穿／3D路徑，而ship平面方案無法表示 | 同座標不同深度的碰撞／路徑需求與重現；說明為何設計限制無法接受 | 查匹配R28原生碰撞／尋路，新增引擎來源固定及Build任務 |
| 精確彈道是必要需求且Mod候選仍失敗 | 位置／速度／時間單位／命中點與HP，兩seed；命中容許誤差在試驗前寫定 | 定位偏差來源後再決定是否改native，不以放大footprint掩蓋 |
| JS更新無法達到預先約定的性能門檻 | T14硬體、單位數、設定、基線與候選p95 turn time、profile；數值門檻先定 | 只對量測到的瓶頸考慮native化；目前未量測，不下性能結論 |
| 存讀檔／多人存在無法由Mod修正的差異 | T13至少雙客戶端、固定版本／輸入／seed，首個分歧或序列化丟失重現 | 先定位狀態／事件錯誤，再比較修改範圍 |

如選D，新增獨立任務：官方R28匹配source與runtime對照 → 可重現Build → 最小補丁 → M1/M2及特殊機制回歸 → 存讀檔／雙客戶端／性能 → 發行與回退方案。不得在舊0.0.27 repo來源上直接宣稱產生R28；沿用既有runtime作回退，版本不同的存檔不假定可互讀。
